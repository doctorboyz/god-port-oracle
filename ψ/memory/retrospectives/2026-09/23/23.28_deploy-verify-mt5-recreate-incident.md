## Blockers & Resolutions

- **train สตาร์ทไม่ได้หลัง deploy**: mt5b/c/d unhealthy ตอน compose ประเมิน depends_on → แก้ด้วยการรอ terminal บูตจร็บ (~30 นาที) แล้ว up train อีกครั้ง — สำเร็จ; root cause คือ start-period 180s สั้นกว่า boot จริง เก็บ ISSUE-090 ไว้แก้ถาวร
- **Monitor false positive**: เงื่อนไข grep "healthy" ตรงกับ "unhealthy" ด้วย — แก้เป็น match `:healthy$` exact

## Honest Feedback

1. **เขียน monitor แล้วไม่ทวนสอบผลลัพธ์ก่อนใช้**: ผมเขียนเช็ค `grep -v "healthy"` แล้วประกาศ ALL_HEALTHY ทั้งที่ event มีคำว่า unhealthy อยู่ตรงหน้า — ถ้าผมเชื่อ monitor ตาบอดและรายงานคุณหมอว่า "ขึ้นครบแล้ว" แล้วไปสตาร์ท train ตอน terminal ยังไม่พร้อม การ deploy จะ fail ซ้ำและหลงคิดว่า bug อยู่ที่อย่างอื่น สิ่งที่ช่วยไว้คือการอ่าน event ด้วยตาก่อนเชื่อ — ที่ผมเกือบไม่ทำ
2. **รู้ว่า deploy จะลาก dependency ไป recreate แต่ไม่ได้เตรียม**: ก่อนกด deploy ผมไม่ได้คิดเลยว่า mt5b/c/d จะโดน rebuild และ recreate ด้วย ทั้งที่เคยเห็นพฤติกรรม compose แบบนี้ — เป็นการ deploy ที่ "หวังให้ผ่าน" ไม่ใช่ deploy ที่วางแผนไว้ก่อน
3. **ตรวจรับรอบนี้ทำดีเพราะถูกบทเรียนเช้าบังคับ ไม่ใช่เพราะผมฉลาดขึ้นเอง**: ถ้าไม่มี retro เช้าที่จดว่า "env ตั้งครบ ≠ config ถูกใช้" ผมจะ echo os.environ อีกรอบแล้วปิดรายงานไปแล้ว สิ่งที่ควรเอาไปต่อคือทำให้การอ่านค่าจาก object จริงเป็นขั้นตอนมาตรฐานของตรวจรับ ไม่ใช่แค่ความจำระยะสั้นหลังโดนด่า

## Lessons Learned

1. **grep "healthy" match "unhealthy" ด้วย** — เวลาตรวจสถานะแบบ substring ต้อง anchor ให้ exact (`:healthy$`) หรือใช้ == กับค่าจริง ความผิดเล็กๆ แบบนี้ใน monitoring ทำให้ระบบโกหกได้
2. **`up -d --build <service>` อาจ rebuild + recreate ทั้ง dependency chain** — ก่อน deploy ต้องถามว่า "image ของ dependency เปลี่ยนไหม" และถ้า container นั้นบูตนาน (mt5 ~30 นาที) ให้ deploy เป็นสองจังหวะ: up deps ก่อน รอ healthy แล้ว up ตัวหลัก
3. **บทเรียนที่เขียนลง retro ตอนเช้าถูกใช้จริงตอนเย็นและได้ผล** — verification จาก object จริง (LiveTrader.risk.risk_reward_ratio) จับค่าถูกในครั้งเดียว ต่างจาก env echo ที่เคยหลอกเรา — ยืนยันว่าการจดบทเรียนแบบ actionable มีค่าจริง
